# Hotel Booking API — Performance Optimization

Основной целью работы являлось:

- уменьшение нагрузки на базу данных;
- ускорение времени ответа API;
- защита API от слишком большого количества запросов;
- изучение подходов кеширования и rate limiting.

## 1. Кеширование данных

Для повышения производительности было реализовано кеширование через Redis.

### Почему было выбрано кеширование

В системе присутствуют операции, которые:

- выполняются очень часто;
- редко изменяются;
- требуют обращения к базе данных.

Наиболее подходящими кандидатами стали запросы на получение списка отелей.

- Получение всех отелей

Endpoint:

GET ```/hotels/```

Кеш:

ключ: ```hotels_all```

TTL: 300 секунд

- Получение отелей по городу

Endpoint:

GET ```/hotels/city/{city}```

Кеш:

ключ: ```hotels_city_<city>```

TTL: 300 секунд

Пример просмотра кеша

```
    docker exec -it hotel-redis redis-cli
127.0.0.1:6379> KEYS *
(empty array)
127.0.0.1:6379> KEYS *
1) "hotels_all"
127.0.0.1:6379> GET hotels_all
"[{\"id\": \"6a0de12f96c389d1fe9df8a3\", \"name\": \"Hilton\", \"city\": \"Amsterdam\", \"address\": \"Center 1\", \"description\": \"Luxury hotel\"}, {\"id\": \"6a0de12f96c389d1fe9df8a4\", \"name\": \"Ibis\", \"city\": \"Paris\", \"address\": \"Street 2\", \"description\": \"Cheap hotel\"}]"
```

- Была выбрана стратегия Cache-Aside (Lazy Loading)

### Алгоритм работы:

1. API проверяет наличие данных в Redis;
1. если данные найдены — возвращается кеш;
1. если данных нет — выполняется запрос в MongoDB;
1. результат сохраняется в Redis;
1. клиент получает ответ.


### Инвалидация кеша

При создании нового отеля выполняется очистка кеша:

hotels_all
hotels_city_<city>

Это необходимо для предотвращения выдачи устаревших данных.

## 2. Rate Limiting

Для защиты API был реализован механизм ограничения количества запросов.

Используемая библиотека - ```slowapi```

На почти все endpoints выл поставлен лимит - 5 запросов в минут, на получение отелей 30, на получение отеля по городу - 20.

Был выбран алгоритм - ```Fixed Window Counter```

### Причины выбора:

- простая реализация;
- подходит для учебного проекта;
- эффективно ограничивает частые запросы.
- HTTP статус при превышении лимита

При превышении лимита API возвращает ```429 Too Many Requests```

 API возвращает дополнительные заголовки:

- X-RateLimit-Limit
- X-RateLimit-Remaining
- X-RateLimit-Reset

## Анализ производительности
### Что было оптимизировано
До кеширования каждый запрос:

- обращался к MongoDB;
- выполнял чтение коллекции;
- сериализовал данные.

Это увеличивало:

- время ответа;
- нагрузку на БД.

После кеширования повторные запросы:

- обслуживаются Redis;
- не требуют обращения к MongoDB;
- выполняются значительно быстрее.

Преимущества Redis в том, что хранит данные в оперативной памяти и в готовом сериализованном виде. Это обеспечивает минимальную задержку и
высокую скорость чтения.

Метрики производительности

Для оценки эффективности можно использовать:

1. Метрики кеширования
- Cache Hit Rate
- Cache Miss Rate
- Среднее время ответа
2. Метрики API
- Requests per second (RPS)
- Average response time
- Error rate
- Количество 429 ответов
